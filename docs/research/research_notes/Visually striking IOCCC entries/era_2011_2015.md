# Visually striking IOCCC winners, 2011 to 2015

Method note (applies to every "observed" item below): I cloned the official winner repo (github.com/ioccc-src/winner, branch `master`, commit 31bd35c dated 2026-09-28; its CNAME is www.ioccc.org, so it is the source of the live site). I read each candidate's README.md and `.entry.json`, drew a silhouette of each original source file, then built and ran the candidates in a `debian:trixie` **linux/aarch64** Docker container (gcc 14.2.0, the same arch and compiler generation as Raspberry Pi OS Trixie on a Pi 4). The runs used a real pty set to **80x23**, and the output went through the `pyte` terminal emulator to capture screens. Items marked "observed" come from those runs, not from a web page. Per-entry pages follow the pattern `https://www.ioccc.org/<year>/<dir>/index.html` (spot-checked: HTTP 200).

## Objective: ranked shortlist of visually striking 2011 to 2015 winners, with fit to the wall

### Takeaway
The contest years in scope are 2011 (20th IOCCC), 2012 (21st), 2013 (22nd), 2014 (23rd) and 2015 (24th). There were no contests from 2007 to 2010, and the next one after 2015 was in 2018. Yusuke Endoh (mame) dominates this era. His **2012/endoh1 (ASCII fluid)** and **2013/endoh4 (rotating ASCII polyhedron)** are the best fits for the wall: pure ASCII, animated, sized to about 80x23, and clean builds on aarch64 gcc 14. His **2012/endoh2 (pi-shaped spigot quine)** is the strongest "code that prints code-as-art" piece. **2011/eastman (Amiga Boing ball)** and **2013/birken (Tetris painter)** look spectacular but draw with ANSI *background colors*, so on a one-color wall they only work if the wall maps background color to lit cells or brightness.

**Per-entry detail**

1. **2012/endoh1: ASCII fluid dynamics.** It reads an ASCII layout (walls and fluid) from stdin and animates a particle fluid simulation in ASCII. It ships 18 scene files, including fountain, pour-out, clock, logo and dripping-pan, and `./endoh1 < endoh1.c` uses its own source as the scene — [README](https://www.ioccc.org/2012/endoh1/index.html)
   - The README warns about flashing. The `alt` build adds `SLEEP` (default 12321 µs between frames) and `TIMER` (a default 10 s alarm, max 60). `endoh1_color.c` is a color variant added at the judges' request. Avoid it on the wall: in my run it painted 256-color backgrounds (`48;5;NNN`) over the whole screen — [README](https://www.ioccc.org/2012/endoh1/index.html); observed
   - Widely known: Hacker News threads, Hackaday "Animated ASCII Fluid Dynamics Simulator Is Retro Cool" (2015), Endoh's YouTube video, and several deobfuscation repos. It fits in an 80x25 terminal — [HN](https://news.ycombinator.com/item?id=20074185); [Hackaday](https://hackaday.com/2015/03/07/animated-ascii-fluid-dynamics-simulator-is-retro-cool/); [HN Theater](https://yahnd.com/theater/r/youtube/QMYfkOtYYlg/)
   - Observed: output is pure ASCII (no color SGR, no non-ASCII), max line width 79, and a scene is 23 input lines. `./endoh1 < endoh1.c` drew about 20 rows, from a basin border up to a splashing surface. It redraws in place with cursor-home (about 15/s for endoh1.c, about 67/s for fountain.txt), not full-screen clears. The build was clean: 0 warnings, 0 errors with the repo Makefile.
   - Source-as-art: 23x79 block lettering that doubles as the fluid's starting layout (silhouette observed). **The best all-round wall candidate.** For the Reduced (15-row) tier, pick or author a shorter scene file.
2. **2013/endoh4: convex polyhedron viewer.** It reads 3D vertices, computes the convex hull (gift wrapping), and renders it in ASCII line art (`"',;;;,;'"`) with a camera on a spiral orbit, without `math.h`. The judges note that the source "is formatted as the net for a tetrahedron", and feeding it its own source renders that solid. It ships a `solids/` directory, including a truncated icosahedron ("football") — [README](https://www.ioccc.org/2013/endoh4/index.html)
   - Observed: the Makefile default is `-DS=70,23`, **exactly the wall's 23 rows**, and `make clobber SIZE=w,h all` can change it for the Reduced tier. Output is pure ASCII and animates forever. It had 0 warnings with the Makefile, and the author says it is C89/C99 clean with `-pedantic -Wextra`.
   - **Risk:** it has no frame delay. It printed about 6 MB (about 84,500 newlines) in 8 s, which is hundreds of frames per second of *scrolling* output. The wall's terminal renderer or flash governor has to cope, or output must be rate-limited outside the program (for example with a pipe limiter).
3. **2012/endoh2: pi/e spigot quine.** The source is "in the shape of a spigot" (a tap). Running it prints a program shaped like the Greek letter π. Each generated program computes one more digit of pi and prints itself as larger pi-shaped ASCII art. With the argument `e` it does Napier's constant instead. It contains a 3x5 digit font packed into 20 bytes, and the author sized it to fit one 80x25 screen — [README](https://www.ioccc.org/2012/endoh2/index.html)
   - Observed: the first stage prints exactly 23 lines by 65 columns (a perfect fit). Compiling and running the next generation gives a 104-line program that scrolls, with the digits drawn in code. Build was clean (0 warnings).
   - The live chain "compile, run, compile the output, run" suits a button that compiles on the wall, and it shows "code as art" literally.
4. **2011/eastman: Amiga Boing Ball.** A raytraced checkered ball bounces over a perspective floor and wall. It sizes itself to the terminal via `ioctl` at startup. The whole raytrace is "a single expression involving 41 operators" — [README](https://www.ioccc.org/2011/eastman/index.html)
   - The judges say it needs "a terminal capable of displaying coloured ANSI characters" — [README](https://www.ioccc.org/2011/eastman/index.html)
   - Observed: every pixel is a *space with a background color* (SGR 40, 47, 100, 101 and 107, meaning black, white, gray, red and bright white). The captured text screen is completely blank. Only when background-colored cells are rendered as lit do you see the ball, and with plain on/off mapping almost the whole screen lights and the red/white checker is lost. It needs a **color-to-brightness map** (for example white full, red mid, gray dim, black off) to read on a one-color wall. It runs at about 12 frames/s (`usleep(79383)`), about 139 KB/s, and built clean.
   - Source-as-art: shaped as a round ball under a short header block (silhouette observed).
5. **2013/birken: Tetris that paints a picture.** It reads a 17-column "paint by numbers" palette file and drops Tetris pieces that fit together into the picture. It ships Mario, Ms. Pac-Man, Samus, Bomberman, an IOCCC logo and others. It also won "Most amusing abuse of the iocccsize tool". The `alt` build has a speed setting (`SLEEP`, default 15000 µs), and the README warns about flashing colors — [README](https://www.ioccc.org/2013/birken/index.html)
   - Observed: pieces are background-colored spaces (SGR 40 to 47), so they vanish on a mono text render unless background colors are lit. `mario.txt` is **32 rows tall**, taller than the 23-row wall, so the wall needs a custom picture file of about 21 rows or fewer. Build was clean.
   - Source-as-art: blocky Tetris-piece silhouette (observed).
6. **2014/sinon: shooter game you play by recompiling.** Each run prints the next program. Firing depends on time since the last compile and on whether it was built with `-O0` (Glock) or `-O2` (Hecate II). `try.sh` includes an **automatic play mode, `perl prog.c | bash`** — [README](https://www.ioccc.org/2014/sinon/index.html); [try.sh](https://github.com/ioccc-src/winner/blob/master/2014/sinon/try.sh)
   - Observed: `./prog` prints a roughly 60-column field of kaomoji enemies (`('A`)`) with "Time / Hecate II / Glock 18C" bars that fit in about 21 rows. The output is itself C source, and one very long line (about 1759 chars) ends in a comment, which would wrap on the wall. Build was clean.
   - Suits a "compiles live" theme very well, but needs perl on the Pi. The source is shaped as a large character figure (silhouette observed).
7. **2011/akari: image downsampler (Best of Show).** It downsamples PGM, PPM or ASCII art. Since "the source code is formatted as ASCII art", `./akari akari.c` produces `akari2.c`, a smaller valid C program (an expander with an optional rot13), and 3 programs are embedded in total — [README](https://www.ioccc.org/2011/akari/index.html)
   - Observed: `./akari akari.c -` prints a 46x21 ASCII-art program (fits), static and instant. The source (43x92) is a character portrait (girl's face and hair, silhouette observed). Excellent portrait; the wall output is a static "shrink the art" reveal.
8. **2014/endoh2: ASCII-to-DNA transcoder.** "This chromosome program synthesizes a double helix. The helix can also be compiled as a C program", following A-T and C-G base pairing — [README](https://www.ioccc.org/2014/endoh2/index.html)
   - Observed: `echo 'Code is Art, A.I. is not' | ./prog` printed a 17-column double helix (`G~~~C`, `T~~~~A`...) 138 lines long. It is instant, so on the wall it needs pacing to read as a scrolling helix. Build was clean, and it compiled with 0 warnings even with a raw `gcc -Wall`. The source is an X-shaped chromosome (32x24, observed).
9. **2011/blakely: Life, reverse Life, and pi.** The source layout is a Game of Life grid that evolves into the digits of pi after 4 generations. `./blakely - < file` searches backward for a predecessor (Garden of Eden check). The author recommends a 60+ row terminal — [README](https://www.ioccc.org/2011/blakely/index.html)
   - Observed: **segfaults on aarch64 with the repo Makefile**, and works when rebuilt with `-fsigned-char`. Generations are printed one after another, so a 60x60 grid scrolls past a 23-row wall. The smaller `3.dat` (13 columns) fits.
10. **2011/hamaji: nonogram solver.** "The source code is a solution to a Paint by Numbers puzzle": `perl c2nono.pl hamaji.c | ./hamaji` reproduces the dragon source image. It ships puzzles including dragon, penguin, samurai, smiley and Game of Life — [README](https://www.ioccc.org/2011/hamaji/index.html)
    - Observed: the dragon solution is 76x47 and the penguin 30x34, both too tall for 23 rows. Smaller puzzles would fit. Build was clean. The source is a dragon (47x76, observed). **Top-tier portrait.**
11. **2015/yang ("Fuuko"): text-to-C encoder.** Output is C90 code that reproduces the input, "filled with pointer dereferences (C stars)" and drawn as sea star patterns that change with the compiler dialect (C90, C99 with eyes, C++98 dango, C++11 circles) — [README](https://www.ioccc.org/2015/yang/index.html)
    - Observed: 79 columns by 104 lines for a short input, so it scrolls. The main `prog` builds clean, but `make all` fails at the C++ variants because the Makefile calls `clang++`.
12. **2015/endoh3: 1984/mullender "emulator".** It runs the famous 1984 mullender entry (PDP-11/VAX machine code in `short main[]`) on a tiny emulator. It needs `make future`, requires a little-endian machine, uses a GCC extension, and hides its architecture name in the source layout — [README](https://www.ioccc.org/2015/endoh3/index.html)
    - Observed: after `make future`, a `:-)` drifts across one line (about 18 B/s). Plain `make all` gave "Illegal instruction ;-(". The linker printed a size-discrepancy warning. Low visual impact, but a great story.
13. **2012/konno: one-liner elementary cellular automaton.** `./konno 30` draws Rule 30. The code assumes 4-byte `int` — [README](https://www.ioccc.org/2012/konno/index.html)
    - Observed: a 31x16 triangle, static and instant. It fits even the Reduced tier.
14. **2013/cable2: handwriting OCR (Best of Show).** "The source is presented as a beautiful moonlit scene, in which a quick brown fox jumps over a lazy dog." Input is a hand-drawn BMP and output is plain text. Its bugs.md says it is little-endian only — [README](https://www.ioccc.org/2013/cable2/index.html); [bugs](https://www.ioccc.org/bugs.html#2013_cable2)
    - Observed: produced **no output on aarch64** until built with `-fsigned-char`, after which it OCR'd `hello_world.bmp` into a 5-line Hello World program. Great portrait, weak wall output.
15. **2011/goren: Magritte tribute ("Most artistic").** It is written with no conditionals of any kind and decides whether text contains a "real" pipe. The author says it "doesn't support 64 bits" but "does work on 64-bit Linux because all functions are below 4GB" — [README](https://www.ioccc.org/2011/goren/index.html)
    - Observed: the source is a framed picture of a pipe (the painting). Output on aarch64 was correct (`|` then "This is a pipe"). Portrait 5, output 1.

**Famous or striking entries that fail the wall constraints (portrait-only candidates)**
- **2015/endoh1** (Endoh & Anonymous, "Most diffused reaction"): a Gray-Scott reaction-diffusion simulation served over HTTP via `tcpserver` to an HTML5 browser. The source is a **portrait of Alan Turing** (the judges point to "`stdeye-o`" and "`<--mouth`"). No terminal mode. — [README](https://www.ioccc.org/2015/endoh1/index.html)
- **2014/endoh1** (Endoh, "Most square (YODA Award)"): a QR-code quine generator, and the **source is a QR code** (silhouette observed). `make treacl` output is 1131 columns by 161 rows of background-colored cells, far beyond the wall. The judges say "Big terminals with tiny fonts have their uses" — [README](https://www.ioccc.org/2014/endoh1/index.html)
- **2015/dogon** ("Most crafty"): X11 Minecraft demo. Source shaped as a Creeper face (observed). — [README](https://www.ioccc.org/2015/dogon/index.html)
- **2012/hamano** (Silver Award, "Most elementary use of C"): its output is a PDF of "little dancing men". Source shaped as a dancing figure (observed). — [README](https://www.ioccc.org/2012/hamano/index.html)
- **2015/mills1** ("For the Birds!"): terminal Flappy Bird built on ncurses, and the source is shaped as the bird (observed). Observed without input: it sits on "Tap to Flap!" forever and needs arrow-key presses. It needs `libncurses-dev` to build. Could only work with injected fake keypresses. — [README](https://www.ioccc.org/2015/mills1/index.html)
- **2013/mills** ("Most timely rendered"): a web server that ray-traces the current time into a progressive PNG. Source is a round clock-like shape (observed). — [README](https://www.ioccc.org/2013/mills/index.html)
- **2011/zucker** ("Most shiny"): a text ray tracer that writes a 600x220 PPM, taking about 78 s on the author's laptop. — [README](https://www.ioccc.org/2011/zucker/index.html)
- **2013/hou**: a progressive ray tracer that writes PPM. The source is an 18-line, 5630-column blob with no shape. — [README](https://www.ioccc.org/2013/hou/index.html)
- **2012/dlowe** (Conway's Game of DEATH): an X11 arcade game. The source is shaped as a 14-cell Life pattern that becomes a glider in 19 generations. — [README](https://www.ioccc.org/2012/dlowe/index.html)
- **2013/endoh2** ("Most recyclable"): a JPEG quine. The first stage prints text 108 columns wide, and the final output is a JPEG. — [README](https://www.ioccc.org/2013/endoh2/index.html)
- **2015/endoh2** ("Most overlooked obfuscation"): the hidden-text trick relies on overstrike/bold in `less`, and the output is just Hello World. — [README](https://www.ioccc.org/2015/endoh2/index.html)
- **2013/cable3** (8086tiny PC emulator): the build needs SDL 1.2 (fails without `SDL.h`, observed), it uses an 80x25 text mode, and it needs a keyboard. — [README](https://www.ioccc.org/2013/cable3/index.html)
- **2011/toledo** (X11 tank game), **2014/maffiodo1** (SDL game homage), **2012/blakely** (animated GIFs), **2011/vik** and **2014/vik** (audio): all fail the output constraints — [2011 list](https://www.ioccc.org/2011/index.html); [2014 list](https://www.ioccc.org/2014/index.html)
- **2015/duble** ("Best handwriting"): Braille-glyph handwriting animation. Observed on aarch64 (even with `-fsigned-char` and a UTF-8 locale): it printed `>` and hung. bugs.md says it "is known to, in some cases, segfault". A 5x7 dot-matrix font is also unlikely to include Braille glyphs. — [README](https://www.ioccc.org/2015/duble/index.html); [bugs](https://www.ioccc.org/bugs.html#2015_duble)

### Inferences
- The strongest set of five for the wall combines 2012/endoh1 (fluid), 2013/endoh4 (rotating solid), 2012/endoh2 (pi quine chain), and then either 2014/sinon (with perl autoplay) or 2011/akari/2014/endoh2 for a static or scrolling piece. 2011/eastman or 2013/birken only belong in the set if the wall renderer maps background colors to brightness.
- Having three or four entries by one author (Endoh) may clash with the plaque concept. Don Yang (akari, sinon, yang) and Birken or Eastman are the main alternatives with different authors.
- The best *portraits* in this era that fail the wall are 2015/endoh1 (Alan Turing), 2014/endoh1 (a real QR code) and 2011/hamaji (dragon).

### Gaps
- I did not verify whether the 2014/endoh1 source is a *scannable* QR code; the README defers to `quine-qr.html`, which I did not read.
- I did not investigate why 2015/duble hangs on aarch64.
- I did not measure how 2013/endoh4 behaves on a real Pi 4 (slower CPU) or how the wall's renderer handles its uncapped scrolling.
- I did not check the source-shape meaning of 2011/zucker, 2013/mills or 2015/yang against author statements beyond silhouettes. The descriptions above are my visual reads.

## Which entries produce terminal-only output that fits 80x23 (mono, no input)?

### Takeaway
Pure-ASCII, no-input, fits 80x23 as observed: **2012/endoh1, 2013/endoh4, 2012/endoh2 (first stage), 2011/akari, 2012/konno, 2015/endoh3, 2014/sinon** (about 60 columns, one overlong comment line). Terminal-only but taller than 23 rows (it scrolls, which is fine for a live terminal but not composed for it): **2014/endoh2, 2015/yang, 2011/hamaji, 2011/blakely, 2014/maffiodo2 (80x52)**. Terminal-only but color-dependent (background-color pixels): **2011/eastman, 2013/birken**.

### Cited Findings
- 2012/endoh1 "is a tiny fluid simulator that fits in an 80x25 terminal" — [HN Theater](https://yahnd.com/theater/r/youtube/QMYfkOtYYlg/). Observed: max line 79, about 20 rows used for endoh1.c, pure ASCII.
- 2012/endoh2: "to make it fit inside one screen (80 x 25), my program is shortened properly" — [README](https://www.ioccc.org/2012/endoh2/index.html). Observed: first-stage output is 23x65.
- 2013/endoh4: Makefile default `-DS=70,23`, adjustable with `SIZE=` — [README](https://www.ioccc.org/2013/endoh4/index.html). Observed build line `-DS=70,23`.
- 2011/eastman sizes itself to the terminal geometry at startup: "The program will size itself to the initial geometry of your terminal" — [README](https://www.ioccc.org/2011/eastman/index.html). Observed: background-color-only pixels.
- 2013/birken needs color, and its README warns about flashing colors — [README](https://www.ioccc.org/2013/birken/index.html). Observed: `mario.txt` is 32 rows.
- Inputs needed (canned input is fine): endoh1 needs a scene file on stdin; endoh4 a vertex file; akari a file argument; konno a rule number; hamaji a `.nono` file; birken a palette file; endoh2 (2014) and yang some stdin text; sinon uses perl for autoplay — per each entry's README (links above).
- Frame and flash observations: endoh1 redraws in place (cursor home, no `2J`), at 15 to 67 redraws/s depending on scene. Eastman runs at about 12 fps, with every frame a full-screen background repaint. endoh4 has uncapped scrolling output (about 750 KB/s). mills1 redraws about 18/s. — observed

### Inferences
- For the Reduced 15-row tier: endoh4 can be rebuilt at `SIZE=70,15`, endoh1 needs a 15-line scene file (output height follows the input layout), and konno (16 rows) nearly fits. endoh2's 23-row pi shape would be cropped.
- Background-color entries (eastman, birken, endoh1_color, 2014/endoh1's QR) need a wall rule that treats non-black background cells as lit or dimmed. If the wall only lights glyph pixels, they display nothing.

### Gaps
- I don't know how the wall's pty renderer handles SGR background colors or reverse video. That determines whether eastman and birken are viable.

## Which build cleanly on modern 64-bit gcc (Pi 4, aarch64, -Wall not -w)?

### Takeaway
Using the **repo Makefiles** (which compile with `-std=gnu11 -Wall -Wextra` plus targeted `-Wno-…` flags, not `-w`), every shortlisted entry built on aarch64 gcc 14.2 with 0 errors, and nearly all with 0 warnings. **Raw `gcc -Wall` with no extra flags fails on about half of them**, because gcc 14 turns implicit-int, implicit-declaration and int-conversion into errors. Two ARM-specific traps: **2011/blakely and 2013/cable2 need `-fsigned-char`** (char is unsigned on ARM Linux).

### Cited Findings
- Repo Makefiles set `CWARN= -Wall -Wextra ${CSILENCE}` with `CSTD= -std=gnu11` and per-entry `CSILENCE` lists. For example, eastman uses `-Wno-implicit-int -Wno-unsequenced -Wno-strict-prototypes ...`, and birken adds `-include stdlib.h` — [2011/eastman Makefile](https://github.com/ioccc-src/winner/blob/master/2011/eastman/Makefile); [2013/birken Makefile](https://github.com/ioccc-src/winner/blob/master/2013/birken/Makefile)
- Observed (`make`, gcc 14.2.0, aarch64): 0 errors for 2011 eastman, akari, blakely, hamaji, goren, borsanyi and zucker; 2012 endoh1 (+alt), endoh2 and konno; 2013 birken (+alt), cable2, endoh2, endoh4, dlowe, hou and mills; 2014 endoh1, endoh2, maffiodo2, sinon and skeggs; 2015 endoh1, endoh2, endoh3, endoh4 and duble. The only warnings were 1 each for blakely (`-Wtype-limits`), cable2 (`-Wsign-compare`) and maffiodo2 (implicit type).
- Observed failures: 2013/cable3 (`SDL.h` missing, needs SDL 1.2 dev); 2015/mills1 (`curses.h` missing, which builds once `libncurses-dev` is installed); 2015/yang (the main binary builds, but the C++ variants call `clang++`).
- Observed raw `gcc -Wall -O2` (default std, no Makefile flags): **errors** for eastman, blakely, endoh1 (needs the `-DG -DP -DV` macros from the Makefile), konno, birken, cable2, 2015/endoh2, 2015/endoh4, duble and goren. **Compiled** with warnings for akari, hamaji, 2012/endoh2, endoh4, 2014/endoh1, 2015/endoh3, yang and 2013/endoh2. 2014/endoh2 had 0 warnings.
- Observed runtime on aarch64: blakely segfaults and cable2 prints nothing unless built with `-fsigned-char`. goren's author warns it "doesn't support 64 bits", but it ran correctly. 2015/endoh3 needs `make future` and little-endian (the Pi is little-endian). 2012/konno "assumes that the size of `int` is 4", which holds on aarch64. — [goren README](https://www.ioccc.org/2011/goren/index.html); [endoh3 README](https://www.ioccc.org/2015/endoh3/index.html); [konno README](https://www.ioccc.org/2012/konno/index.html)
- The IOCCC repo tracks known issues per entry with statuses such as "INABIAF - please DO NOT fix" (for example 2013/endoh4, 2013/cable2, 2015/duble, 2014/maffiodo2) — [bugs.html](https://www.ioccc.org/bugs.html)

### Inferences
- The installation should build from the ioccc-src/winner copies using each entry's own Makefile, which satisfies "-Wall, not -w". It should also add `-fsigned-char` for blakely and cable2, or simply for everything, since x86-era IOCCC code assumes signed char.
- Test on the Pi itself before committing: the container matches arch and compiler but not CPU speed, and endoh4 and endoh1 timing will differ.

### Gaps
- I didn't test gcc 12 (Raspberry Pi OS Bookworm). Its implicit-int handling is more permissive than gcc 14's, so raw builds would likely fail less often, but I did not verify this.
- I didn't test on real Pi hardware or the actual wall pty.
